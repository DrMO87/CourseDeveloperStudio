# STEP 9 Phase A — proposed digestion and review fixes

## 1. Plain-English summary

Academy-brain currently copies teaching text out of slides and then mostly checks whether files exist for the work that should follow; it does not reliably turn that text into a clear explanation, check the explanation against its sources, resolve review findings, or carry the result into the final lesson. The proposed changes would turn supplied material into a sourced session explanation, a practical learning activity and answer key, independently reviewed corrections, and matching English and Arabic content that actually reaches the deck generator. Dr. Mahmoud would be able to see what each session teaches, where that understanding came from, and which missing facts still prevent delivery. MVP offers useful mechanisms for input-quality checks, version tracking, bounded AI drafting, and consistent output rendering, but several review stages need academy-brain-native work. These are recommendations for human review; this document authorizes no implementation.

## 3. Per-stage design details

### Common proposal boundary and worked fixture

The ticket's DEC-007/008/009 rationale (`docs/tickets/2026-09-04-academy-brain-mvp-integration.md:53–59`) supports scoped capability transfer and academy-brain-native fixes; it does not authorize STEP 8b or implementation. STEP 5 already supplies the real pedagogy gate result through the adapter (`docs/tickets/handoffs/step5-academy-brain-adapter.md:99–123,138–170`). This proposal would author and review the content that supports that result, not replace or duplicate that gate. The current implementation reads `30-research/1-pedagogy.yaml` for `L1-s1` (`academy-brain/scripts/swarm/generate_session.py:919–932`), a detail addressed in R2.

Use this deliberately small synthetic fixture to evaluate each proposed capability: course `loop-foundations`, session `L1-s2`, objective **O1: trace a fixed-count loop and explain which statements repeat**. Supplied PDF page 4, or equivalent PPTX slide 4, says: “Repeat the body 3 times. Each iteration draws one mark.” Its notes say: “Compare with statements outside the loop.” A second page contains a diagram whose text extraction is unreadable. These are example inputs, not claims about Dr. Mahmoud's actual curriculum. Course title, audience, objectives, source assignments, provider choices, session count, and language policy would come from that course's configuration and reviewed records, never from this example.

Across R1–R10, recommend a **versioned academy-brain stage-evidence contract**: course identity, scope, session/level, stage, schema version, input and output hashes, author/reviewer run identities, referenced claims, holes, and validation result. These are proposed fields, not fields claimed to exist today. Store extensions in separate metadata records referenced by the existing artifact, so `Envelope`'s current status vocabulary and serialization need not be repurposed (`academy-brain/scripts/swarm/envelope.py:13–26,29–78`). Keep one writer per artifact and publish a new revision only after checking its predecessor hashes under a course/session lock. Cache identical input snapshots; an upstream change makes only its dependents stale. Model-produced references must resolve to real supplied segments; matching hashes prove identity, not factual correctness.

This explicitly proposes strengthening **what counts as stage evidence** for new work. Simply adding authoring calls while retaining `check_stage()`'s arbitrary-file success would leave the defect open. Keep stage ordering, existing stage names, structured waiver vocabulary/scope/expiry rules, and historical locked-golden treatment (`academy-brain/scripts/swarm/stage_gate.py:64–75,89–168,188–228`). Recommend a new doctrine version for stronger evidence validation, without reinterpreting old receipts or regenerating locked PDFs. A waiver records an exemption, not semantic validation; downstream stages must carry its missing-evidence limitation and must not manufacture the waived content. Legacy drafts can remain readable but would need fresh evidence for a new semantic workflow; no bulk conversion or automatic re-review is proposed.

The three implementation approaches considered are: **skip** improving only gate labels, because that adds no content work; **skip** one unrestricted whole-course AI call, because it loses source boundaries and independently reviewable revisions; **recommend** bounded stage authoring with deterministic validation and independent review. Provider/model and prompt versions would be recorded per authoring attempt, with course-level spending limits and bounded retries. Provider failure or exhausted review budget would leave a visible pending/failed result, never a generic substitute presented as source-derived content. This proposal makes no provider calls.

### 3.1 R1 — Receipts: quality-aware extraction followed by sourced claims

**Before.** A `<session>.gates.yaml` or `<session>.production.yaml` can match the broad receipt glob even though it is not the specialist's claim record. The two writers have distinct payloads (`academy-brain/scripts/swarm/gate_runner.py:44–66`; `academy-brain/scripts/swarm/generate_session.py:935–944`). The PDF SOP instead calls for a frozen specialist receipt and a second agent checking it against raw PDFs (`academy-brain/00-contracts/pdf-intake-sop.md:84–92`).

**After/example.** The proposed specialist record contains C1, “The example executes its loop body three times,” supported by the page-4 excerpt; C2, “This example draws one mark per iteration,” with its own support; and H1, “Page 5's diagram cannot yet be read.” The independent receipt reviewer checks both C1 and C2 against the original page or slide, not just the specialist's text. H1 remains a hole and cannot become a purported diagram interpretation.

**Design and transfer.** Adapt MVP's normalized-text/quality-report separation and explicit extraction failure reporting (`MVP/src/server/source-intake/service.ts:223–279,376–435`), then add the native specialist author and independent verifier prescribed by the SOP. Validate receipt kind and required claim structure, rather than accepting every matching YAML. Preserve distinct gate/production receipts. Resolve the runtime course's intake schema referenced by the SOP before authoring; `knowledge/_schema/intake-schema.yaml` is a course-content dependency referenced at SOP lines 61–66 and 84–88, not present in the inspected monorepo file listing. This proposal does not invent a replacement schema or assert compatibility with an unseen course copy. The stage-evidence metadata above would be an extension alongside it.

**Scale/format mismatch.** MVP's `SourceDocument` is unique per lesson (`MVP/prisma/schema.prisma:176–188`). Academy-brain needs many versioned sources, sources shared across sessions, and explicit page/slide/paragraph assignments. Normalize each source once; preserve a segment-to-original map. PDF text, Office body text, notes, and OCR would remain distinguishable evidence channels. An unreadable scan needs a visible extraction limitation or separately reviewed OCR, not silent omission. Do not inherit MVP's lesson-sized truncation or infer session ownership from deck order.

**Compatibility and review criterion.** Do not edit raw files, licenses, catalog authority, or frozen receipts; a correction is a new review/revision. Adapt extraction mechanics, not MVP's Prisma table or project state machine. A future demonstration should show that an ordinary gate receipt cannot satisfy the sourced-receipt requirement, and that H1 survives into the digest. R3 and R4 depend on this capability or equivalent genuinely sourced manual receipts.

### 3.3 R3 — Digest: actual synthesis without losing extraction evidence

**Before.** The current result repeats the fixture as a slide heading, body, and separate notes. `run_digest.py` neither reads the specialist receipt nor synthesizes it; its warning-dependent envelope status describes extraction success, not understanding (`academy-brain/scripts/run_digest.py:44–89`).

**After/example.** Under O1, the proposed digest would say: “A fixed-count loop repeats the statements inside its body, so the supplied three-repeat example runs that body three times [C1]. Because this example draws one mark per iteration, tracing it produces three marks [C2]. Compare those repeated statements with the statements outside the loop to explain which actions repeat [source notes; teaching activity A1].” Separately record prerequisite “read a sequence of statements,” the misconception “all statements on the page repeat,” and H1. The prerequisite and misconception are labeled instructional proposals unless supported by a cited source; they must not be laundered into sourced factual claims.

**Design and transfer.** Keep `digest_office.py` mechanical. Introduce a course-bound intake dispatcher and a separate synthesis operation consuming reviewed receipts, source segments, and R2 research. Its structured result would contain objective IDs, explanatory segments, supporting claim IDs, prerequisites, relationships, teaching choices, contradictions, and holes; render that as the existing digest Markdown plus separate machine-readable evidence. Distinguish notes from body text and preserve conflicting passages rather than choosing one silently.

MVP's `buildSourceDigest()` is useful for source-span selection but uses heuristics and small caps: four core facts, limited definitions/examples, and a default 450-character selected-snippet budget (`MVP/src/server/first-route/source-digest.ts:30–88`). Its serialized categories contain additional text; 450 is not a cap on the whole serialized digest. Real AI work occurs later through `draftSourcePackContent()` with schema/requirements checks and bounded attempts (`MVP/src/server/first-route/source-pack-service.ts:108–174,192–255`). Adapt that execution discipline for synthesis with an academy-brain schema, including exact source references and declared uncertainty. A structurally valid result still needs R4/R5; schema validity alone is not semantic quality.

**Scale/format mismatch.** Replace dependence on the runner's `SOURCE_MAP` with explicit source-to-session range assignments resolved from the course root. Extract PDF segments and PPTX/DOCX segments through format-specific adapters; DOCX's current paragraph-only helper is not equivalent to a page-preserving PDF extractor. Chunk by source boundaries, summarize into session scope, then reconcile a level concept index; never send an entire course through MVP's lesson caps or trim off late-session material without notice. The existing `CoursePaths` supplies configured session IDs and artifact eligibility (`academy-brain/scripts/swarm/paths.py:14–45,72–75`); reuse it instead of inventing a parallel ID system.

**Compatibility and review criterion.** Preserve extracted content as a separate immutable record, existing image names/manifest fields, source binaries, and current envelope vocabulary. Explicitly change `10-digest/<session>.md` from slide dump to objective-linked synthesis, retaining links to the extraction record. Skip importing MVP's `PlaceholderSet` inference as the fix: it copies lines after recognized objective headings (`MVP/src/server/placeholders/proposal.ts:27–35,59–84`); its useful draft/edit version lifecycle (`MVP/src/server/placeholders/service.ts:103–143,206–250`) is a pattern, not an understanding engine. A future demonstration should show the three-sentence explanation, complete claim links, and H1, and should stop honestly on provider failure. Visible deck benefit also depends on R10.

Use source-qualified IDs and deduplicate by source revision, not by identical excerpt text alone. Do not equate a policy-guide fingerprint with a factual citation. Recommend adapt; no MVP component supplies complete entailment review. ### 3.5 R5 — Critique: three independent, located reviews

**Before.** A single JSON with no substantive review can meet the stage-presence gate. Even an `issues` payload with arbitrary nonempty citation strings can pass the cite filter. ENGINE instead describes three independent lanes (`academy-brain/docs/ENGINE.md:58`).

**After/example.** Give all lanes the same draft revision, R2 task/key, R4 evidence, and raw source references. Lane one returns I1: high severity, D1, “Draft says four executions; source C1 says three,” with the exact source locator. Lane two returns I2: “O1 asks learners to trace, but the draft only gives a definition; include A1,” citing the objective and research task. Lane three checks that an unreadable diagram has not been described as known, and records what it inspected even if it finds no issue. These are sample findings for a deliberately defective draft, not reported defects in a real course.

**Design.** Introduce native review invocation and collection. Each lane gets a fresh context and identical frozen inputs, no other lane's conclusions, and no permission to overwrite teaching content. Preserve the documented codex/opencode/hermes lanes; provider availability is taken from course configuration. An unavailable required lane is missing review evidence, not an empty successful response. Store lane identity, model/run, input hash, checklist coverage, and structured issues with stable IDs, severity, location, explanation, cited support, and suggested correction. Keep existing `issues`, `loc`, and string `cites` compatibility while validating citation resolution through R4. A zero-issue result needs an explicit review record; an empty JSON file is insufficient.

**Why native LLM review.** Factual scope and whether a task truly exercises an objective require contextual judgment. Deterministic checks should resolve citations and verify structure, but cannot perform that judgment. MVP's scanner remains useful in its own pipeline; this proposal does not claim its invocation is independent review or import its algorithm. Separate runs reduce shared-context bias but do not guarantee correctness; unresolved material questions remain visible.

**Scale/format, compatibility, and criterion.** Review one session plus its prerequisite/level context, fetching raw PDF pages or Office slides when evidence needs checking. Do not clone whole-course content into every lane or assume Micro:bit terminology. Keep JSON lane locations, original drafts, and English-only critique; Arabic authoring stays outside these lanes. Recommend adopt. A future demonstration should catch I1 and I2 with resolvable citations and reject a missing or stale lane. R6 depends on this full review set or explicitly represented waivers.

### 3.6 R6 — Patch: adjudication plus a new, inspectable revision

**Before.** `50-patch/<session>.md` can contain only a heading and still satisfy presence. The scaffold's owner/reviewer labels are not a content-changing operation.

**After/example.** JUDGE evaluates I1 against C1 and proposes replacing “four executions” with “three executions.” For I2, add A1 and its separately designated answer key. If a lane proposes adding nested loops, record a withheld disposition because the source set does not support that expansion. The patch record shows exact old/new text, issue IDs, source support, rationale, and the resulting draft revision; conflicting lane suggestions get a reasoned disposition rather than majority voting.

**Design.** Use an academy-brain-native adjudicator to produce a structured patch proposal. Preserve the topology's codex writer and Claude reviewer (`academy-brain/scripts/scaffold_vault.py:39`); JUDGE names a function in this proposed workflow, not a new permanent provider. A deterministic applicator checks expected old text and base hash, applies only located replacements to a new candidate revision, and records resulting hashes and changed claim/task IDs. Re-run source-reference, task/key, and boundary checks on the candidate before forwarding it. Never let an LLM execute arbitrary file edits as the adjudication mechanism.

**MVP comparison.** `redraftSourcePack()` calls whole-pack generation; it does not adjudicate individual lane issues (`MVP/src/server/first-route/source-pack-handoff-service.ts:167–191`). Likewise, the completeness repair call at `MVP/src/server/first-route/source-pack-service.ts:177–180` is an adjacent content operation, not evidence of a general patch adjudicator. Skip both as substitutes.

**Scale/format, compatibility, and criterion.** Locations refer to stable session segments rather than slide numbers alone; a shared research-key fix creates dependent session work, not an invisible course-wide edit. Do not modify the PDF/PPTX or frozen receipt to make a correction appear supported. Keep patch Markdown, original revisions, and the stage chain. Refuse application if the base draft changed, or if two changes overlap incompatibly. Recommend adopt. A future demonstration should show that only adjudicated text changes, and that unsupported scope expansion remains withheld. R7 consumes the new candidate and full adjudication record.

### 3.7 R7 — Refutation: try to disprove high-severity corrections

**Before.** A refutation file can satisfy the gate without examining a patch. ENGINE specifies a refutation pass for high-severity patches (`academy-brain/docs/ENGINE.md:60`).

**After/example.** Suppose a proposed patch changes an overly broad statement to “Any three-repeat loop draws three marks.” The refuter constructs a counterexample with two draw statements per body execution. The revised claim fails that challenge; the narrower wording “This supplied one-mark-per-iteration example draws three marks” is the candidate that should proceed to another check. The counterexample is labeled a review thought experiment, not source material to add automatically to the lesson.

**Design.** A fresh reviewer sees the base draft, patch, sources, and severity, and independently derives what would falsify each high-severity fix. It records patch ID, challenged assertion, source-based reasoning or counterexample, result, and residual uncertainty. Use a different execution identity/context from the patch author and adjudicator; the static shared codex owner labels do not establish independence. The configured topology would need to express this role separation explicitly. If an independent reviewer is unavailable, record missing evidence rather than relabeling the author as refuter.

One pass covers every high-severity patch in the current revision. A defeated patch returns to R6, which creates a new revision; a bounded repeat cycle then reviews that changed patch. Budget exhaustion leaves the disputed issue open. If there are no high-severity patches, emit a reasoned applicability record tied to the actual patch inventory, not an invented successful challenge.

**Scale/format, compatibility, and criterion.** Include dependent session/prerequisite context so a locally correct change cannot silently contradict a shared definition. Source access retains PDF/Office locators and raw-image access; no device-specific counterexample template is assumed. Preserve all previous patch/refutation files as history and the canonical Markdown output path for the current record. No MVP equivalent was identified in the inspected intake, governance, drafting, and handoff paths. Recommend adopt. A future demonstration should defeat the broad three-marks claim, retain the counterexample record, and prevent R8 from proceeding with that unresolved high-severity issue.

### 3.8 R8 — Approval: settle a specific English revision under the existing authority model

**Before.** `enforce_blueprint_gate()` already does more than a loose string search: it requires exact status, nested typed authority, and no unresolved gap markers. Preserve those checks. What is missing is an evidential link from that metadata to the actual reviewed English revision and review outcomes.

**After/example.** The system presents candidate English revision E2 containing O1, the narrow three-mark explanation, A1/K1, the source references, and all adjudication/refutation outcomes. Its decision record would bind E2's hash to the source/research/review hashes and the competent authority. If K1 changes later, the old decision remains historical but cannot release the new revision. An unresolved relevant H1 stays a routed gap; it is not removed merely to satisfy the blueprint check.

**Design and transfer.** Adapt MVP's exact-attempt/content/input binding and recheck immediately before recording the decision (`MVP/src/server/first-route/source-pack-handoff-service.ts:47–70`), and preserve history on invalidation (`MVP/src/server/first-route/source-pack-invalidation.ts:3–19`). Extend this locally to English content and its dependency graph, with the resolved review ledger as a prerequisite. The decision record would include actor/role, time, reviewed hashes, disposition and rationale. A content author cannot grant itself the whole council's decision by writing metadata. If a hole is outside the session's intended scope, a documented scope disposition must explain why; removing a required objective to escape the hole would itself require a new reviewed scope decision.

**Scale/format mismatch.** MVP has teacher approval for one pack. Academy-brain has `specialist_council`, `owner_business`, and `physical_action_required` routing (`academy-brain/scripts/swarm/generate_session.py:175–177,229–300`), plus cross-session dependencies. Preserve that allocation: technical matters go to the specialist/reviewer/refuter process, genuinely business or physical matters go to the relevant human authority. Use per-session decisions and a level dependency index, not one course-wide approval boolean. Source formats matter through their revision hashes, not through a PDF-only approval model.

**Compatibility and review criterion.** Keep `60-approved/<session>.md`, blueprint status/authority/gap semantics, and historical records. Do not confuse the generic envelope's status vocabulary with blueprint approval fields. English content settlement and a later bundle compatibility check do not grant owner live-fire authorization, which the SOP separately requires (`academy-brain/00-contracts/pdf-intake-sop.md:99–114`). Recommend adapt. A future demonstration should make an answer-key edit invalidate only dependent current decisions and should refuse a self-asserted council record without the corresponding reviews.

### 3.9 R9 — Localization: preserve meaning in aligned Arabic segments

**Before.** A localized file can exist without translation; character counts cannot detect a dropped negation, changed number, or code mistranslation. NotebookLM's later Arabic generation does not establish a reviewed localized source artifact.

**After/example.** The proposed alignment includes English segment E2.1, “Repeat the body three times,” and Arabic segment A2.1, “كرّر الأوامر داخل الحلقة ثلاث مرات”, both linked to C1. The next segment preserves “one mark per iteration” and C2, rather than generalizing all three-repeat loops to three marks. A terminology record maps “loop body” to the chosen Arabic term and keeps executable identifiers unchanged. An omitted “not” or changed 3 would be a blocking mismatch.

**Design.** Claude authors the localized copy from R8's settled English snapshot, an explicit course glossary, audience, and language policy; it does not add new subject-matter claims. Validate segment/claim coverage, numbers, units, protected code strings, and source/English hashes deterministically. A separate Claude review context compares meaning and teaching intent and returns located corrections; it is not one of the English critique lanes. Meaning-changing corrections route back to the relevant earlier stage rather than being concealed as translation edits. Run existing language/boundary gates in addition to this check, never as a substitute for it. ENGINE's Claude-only Arabic rule is retained (`academy-brain/docs/ENGINE.md:62`).

**Scale/format mismatch.** MVP language selection is not a bilingual alignment mechanism. Source locators must survive PDF/Office intake through English into Arabic; do not re-extract the PDF as a new unrelated translation source. Do not hardcode a 30/70 mix into this new authoring design. **Compatibility and review criterion.** Preserve the English snapshot, existing localized Markdown location, code/assets, Claude ownership, and gate interfaces. ### 3.10 R10 — Bundling: turn reviewed understanding into generator inputs

**Before.** `build_plan()` uploads `slides-source.md` and `decisions.md` for decks, and `home-summary.md` for the summary; it does not load the digest, provenance, or localized content. `reconcile_slides()` checks asset resolution but does not author a lesson. Therefore an excellent digest by itself still changes nothing in the generated deck.

**After/example.** A versioned session content record would render:

- `slides-source.md`: O1's reviewed explanation, a trace prompt for A1, and the appropriate mapped visual, using existing slide/asset syntax.
- `blueprint.md`: sequence, timing drawn from the course requirements, objective/task relationships, and the existing authority metadata with its reviewed-content binding.
- `decisions.md`: source-bound choices and exclusions that may guide generation; no learner-inappropriate answer-key leakage into student copy.
- `SOURCES.md`: C1/C2, source revisions, locators, and transformations used by this bundle.
- `ASSET-MAPPING.md`: stable asset IDs, destinations, existing table columns, class, actual file path and production status; an actual captured trace image is EVIDENCE, not a redrawable illustration.
- `home-summary.md`: the same explanation in the reviewed target language plus the learner-facing practice prompt. Keep K1 in the designated research/teacher material unless the reviewed teaching sequence explicitly calls for showing an answer.

**Design and transfer.** Adapt MVP's separation between persisted validated content and deterministic artifact rendering (`MVP/src/server/first-route/source-pack-service.ts:224–235,367–408`). Build a native session record from R8/R9, the digest, R2 tasks, R4 evidence, and resolved assets. Author the instructional sequence before its settlement, then render the six files without new factual invention; if bundling discovers a need for new teaching text, route it back through review rather than adding a post-approval AI rewrite. Validate cross-file IDs, objective coverage, numbers, source/asset links, content hashes, and student/trainer boundaries. Check the blueprint's binding again against the exact rendered bundle. Preserve existing image checks (`academy-brain/scripts/swarm/generate_session.py:307–398`) and evidence overlay behavior (lines 434–458,563–599).

**Scale/format mismatch.** MVP produces one source-pack PDF and guidance Markdown; academy-brain requires six Markdown files, session assets, potentially multiple deck passes, and a summary. Do not substitute MVP's filenames or fixed pack schema. Source/asset identifiers must be course-qualified internally even when display filenames are session-local. Do not copy MVP's three-image ceiling, Arabic-description requirement, or `IMAGE-NN` naming wholesale (`MVP/src/server/first-route/governed-input-service.ts:14–16,145–165,402–406`). A repeated source image can serve several sessions with separate pedagogical roles, and an unreadable PDF diagram cannot become a “produced” evidence asset through bundling.

**Compatibility and review criterion.** Preserve the six filenames, Markdown parser shapes, optional deck-b behavior, source/evidence distinction, and current generation result contract. New lineage is additive metadata. MVP's `SourcePackAttempt` and its historical `contentSource` values remain untouched; no generic fallback is introduced. Recommend adapt. A future demonstration should trace C1 through digest, reviews, English/Arabic alignment, the actual uploaded slide text, and the home summary; changing C1 should make the dependent bundle stale. This capability depends on the preceding content stages or equivalent explicitly reviewed manual artifacts.

### 3.11 Limited generation integration companion to R10

**Recommendation: adapt input freshness; skip replacing real generation.** Generation already calls NotebookLM (`academy-brain/scripts/swarm/generate_session.py:819–878`). R10 would close the missing content handoff by populating the files that `build_plan()` actually reads. Do not upload the entire raw review history and hope NotebookLM reconstructs the intended lesson, and do not fold STEP 11's prompt-authoring comparison into this work.

A specific additional integration gap is visible in `_run_pass()`: notebooks are reused by title and uploads with existing titles are skipped (`academy-brain/scripts/swarm/generate_session.py:722–738`); an existing pass PDF with no task sidecar also skips generation (lines 746–767). Consequently, revising `slides-source.md` from four executions to three under the same filename could leave old notebook sources or a previous PDF in use. The recommendation is to bind each generation attempt to a fingerprint of the exact rendered bundle, upload bytes, assets, and existing prompt version, borrowing the exact-input freshness principle from `MVP/src/server/first-route/source-pack-service.ts:224–255,390–407`.

On an identical fingerprint, preserve current resume/no-refire behavior. On a mismatch, stop with a plain reason before spending quota; do not silently delete notebook sources, reset task locks, overwrite outputs, or regenerate locked goldens. An explicitly authorized new generation revision would receive isolated notebook/output identity and its own input manifest; legacy attempts without that manifest remain historical and cannot be asserted to match a new bundle. This is an explicit future change to internal revision identity, not to public deck filenames or the job result schema. Keep the current two-line task sidecar format (lines 611–623), exclusive execution lock, pending-task recovery, EVIDENCE overlay, and final visual-review requirement (lines 935–943). A future demonstration should show that a revised bundle cannot reuse stale sources or PDFs, while resuming an unchanged attempt makes no new generation request. No live generation or implementation is part of this proposal.

## 4. Pipeline boundary and review scope

**No proposal requires collapsing MVP's and academy-brain's pipelines.** All transfers above are mechanisms adapted behind academy-brain's own course-stage contracts. A shared stateless extraction utility could be considered separately, but none of these recommendations depends on one.

These are dependency groupings, not authorization to implement a batch.
